# Weekly 가이드: 주간업무보고 + OKR

산출물: `20. Area/23. 주간보고·OKR/Weekly/YYYY_MMDD-MMDD_weekly-okr.md` **새 파일 1개** (예: `2026_0714-0728_weekly-okr.md`)

한 파일이 세 부분으로 구성된다:

| 부분 | 독자 | 서식 |
|---|---|---|
| Part 1: OKR | AI (Monthly/Quarterly 재료, 상세 아카이브) | 위키링크·정량 수치·상세 허용 |
| Part 2: 주간업무보고 | 사람 (사내 시스템/메일에 붙여넣어 제출) | 붙여넣기 즉시 제출 가능한 텍스트 |
| 관련 노트 | 탐색용 | 위키링크 모음 |

**Part 2가 이 스킬의 성패를 가른다. 사용자가 제출 전에 다시 고쳐 써야 하면 실패다.**
상세 내용의 저장소는 Part 1이고, Part 2는 그 증류본이다.

전역 문체 규칙 (보고서 전체 적용):

- **em dash(`—`) 사용 금지.** 연결이 필요하면 콜론(:), 쉼표, 중간점(·), 괄호를 쓴다. 이 문서에 보이는 `—`는 금지 대상 문자를 표기하기 위한 인용일 뿐이다.
- **'주말'은 어디에도 쓰지 않는다.** 휴무 표기는 평일 휴무(연차·공휴일)만 다룬다.

## 1. 기간 결정

```
사용자가 기간을 지정하면 그대로 사용.
지정 없으면:
  prev_end = Weekly/ 파일명(YYYY_MMDD-MMDD)들 중 가장 늦은 종료일
  start    = min(지난주 월요일, prev_end)   # 공백은 시작일을 당겨서 메운다
  end      = 오늘 (작성 당일 포함, 보통 화요일에 작성)
```

용어 정의:

- **중첩** = start ~ prev_end 구간, 양끝 포함 일수. 경계일 1일 중첩은 정상이다(화요일 작성 주기의 특성).
- **공백** = prev_end 다음날 ~ 지난주 월요일 전날 사이의 미커버 일수 (오늘까지의 거리가 아니다).

처리 규칙:

- 중첩 1일(경계일): 일별 활동 해당 행에 `_(직전 주간 중첩)_`만 표기. ⚠️ blockquote는 생략.
- 중첩 2~3일: 상단에 `> ⚠️` 중첩 blockquote 필수 + 행 표기. 상세 서술은 신규 구간 중심.
- 중첩 4일 이상, 또는 공백 15일 이상: 계산 결과를 제시하고 사용자에게 확인.
- 직전 보고서가 "진행"으로 남긴 업무가 이번 기간에 완료됐으면, 중첩 여부와 무관하게 이번 보고서에 완료로 승계 기재한다.
- prev_end가 오늘보다 미래면 이상 상태이므로 사용자에게 확인.
- Weekly 폴더가 비어 있으면(첫 실행) 기간을 사용자에게 확인.
- **작성을 시작하기 전에, 결정된 기간과 근거를 한 줄로 보고한다.**

## 2. 소스 수집

날짜의 진실은 **파일명**이다. 노트의 `date created`는 몰아서 백필되므로 신뢰하지 않는다.

1. **데일리 노트** (뼈대: 날짜·주제): `20. Area/23. 주간보고·OKR/23-1. Daily/YYYY-MM-DD.md`
   - 2026-05-07 이후 형식: `## Schedule` → `#### Event` 아래 불릿만 유효. `#### TODO` · `## Log` · `## Note-taking`(dataview)은 항상 빈 보일러플레이트이므로 읽지 않는다.
   - 2026-05-06 이전 형식(과거 기간 재생성 시): `## Summary` · `## Schedule`(인라인 `#okr` 태그가 있으면 추론보다 우선) · `## Achievements` · `## TIL`.
   - `YYYY-MM-DD.md` 정규 파일명만 채택. `(conflict …)` 등 Drive 충돌 사본은 무시하고 발견 사실만 고지.
   - 기간 내 평일 데일리가 다수 부재/0바이트면 Google Drive 동기화 문제일 수 있다. 경고하고 중단.
2. **작업 로그** (상세의 주 원천): `10. Project/11. Log/*_log.md`
   - Grep으로 기간 내 `# [[YYYY-MM-DD]]` 헤딩이 있는 파일을 찾아 해당 날짜 섹션만 읽는다.
   - 같은 날짜 아래 세션 종료 스냅샷이 반복 기록된 파일이 있다. 동일 사실은 1회만 채택하고, 서술이 상충하면(진행→완료) 파일 내 나중 서술을 채택.
   - **제외 대상**: ① 이 스킬이 보고서를 생성한 세션의 기록(주간보고 생성 요약 등, 순환 참조 방지) ② 업무와 무관한 개인 프로젝트 로그.
3. **프로젝트·회의·세미나 노트**: `10. Project/**` · `20. Area/21. 팀 운영/` · `30. Resource/34. 세미나·교육/`
   - 기간 내 수정된 파일을 후보로 삼되, mtime은 Drive 동기화로 튈 수 있으니 후보 필터로만 쓰고 내용의 날짜 언급으로 기간 관련성을 확정.
   - 정량 수치·판정·산출물 노트 제목, 그리고 **Confluence/Jira/Figma URL**(Part 2 링크용)은 여기서 얻는다.

### 업무 연속성 정규화 (수집 후, 작성 전 필수)

데일리 노트는 대충 적힌다. 어제와 오늘 표현이 달라도 같은 업무일 수 있다(예: "stt 비교중" / "qwen-caret 비교" / "파이프라인 구성"은 전부 같은 업무). 수집한 항목을 **업무 단위로 클러스터링한 뒤** 작성한다.

- **같은 업무 판정 근거** (하나라도 해당하면 병합): 같은 작업 로그 파일에서 나온 활동 / 같은 프로젝트·산출물 노트를 가리킴 / 같은 대상(제품·모델·기능·저장소)을 다룸.
- **판정이 애매하면 로그가 근거다**: 데일리 표현만 비교하지 말고, 해당 날짜의 로그 섹션에서 실체(저장소·파일·산출물)를 확인해 같은 흐름인지 판별한다.
- **Part 2에서 병합된 업무 = 1개 항목**: 기간 `(M/D~M/D, 상태)`로 표기하고, 일자별 진행은 하위 상세로.
- **제목은 직전 보고서를 따른다**: 직전 보고서에서 "진행"으로 승계된 업무는 직전 보고서의 제목을 그대로 재사용한다(주차가 바뀌어도 표현이 흔들리지 않게). 업무의 성격이 실제로 바뀌었을 때만 제목을 바꾼다.
- Part 1 일별 활동 표에서는 날짜별 행이 유지되지만, 같은 업무는 같은 명칭으로 적는다.

### 무인(자동) 실행 모드

스케줄러(launchd 등)로 사용자 없이 실행될 때:

- 질문하지 않는다. 최선 판단으로 진행하고, 확인이 필요했던 항목은 파일 맨 끝에 `%% 확인 필요: ... %%` 주석으로 남긴다.
- 산출 파일명이 이미 존재하면 **덮어쓰지 않고 중단**, 사유를 출력한다. (대화 모드에서는 사용자에게 확인)
- 당일(작성일) 데일리가 아직 비어 있으면 당일 활동만 생략하고 진행한다. 기간은 그대로 오늘까지.

## 3. OKR 태그 추론 (Part 1용)

데일리 노트에는 `#okr` 태그가 없다(2026-03 이후). **태그는 항상 `okr-master.md`의 매핑 태그 표에서 추론한다.**

- 접두어 → 상위과제: `ai활용/`→1 · `제품/`→2 · `검토/`→3 · `신규/`→4 (과제 제목·가중치·KR 문안은 okr-master가 원본).
- 한 활동에 복수 태그면 ` · `로 병기. 어떤 태그에도 맞지 않으면(전사 행사·팀 회의·휴무 등) `#기타`.

- 휴무 판정: 데일리 본문의 연차/휴가/휴무/반차/공휴일 언급이 근거다(공휴일 표를 하드코딩하지 않는다). 평일인데 데일리 파일 자체가 없으면 휴무로 단정하지 말고 질문 목록에 추가.
- `> 휴무:` 줄에는 **평일 휴무(연차·공휴일)만** 쓴다. 주말은 쓰지 않으며, 평일 휴무가 없으면 줄 자체를 생략.

## 5. Part 1: OKR (AI·아카이브용)

### `## 일별 활동`

`| 날짜 | 활동 내용 | OKR 태그 | 상태 |` 표. **기간 내 모든 평일**이 행으로 존재해야 한다(연차·공휴일 포함). **주말은 행으로 만들지 않는다.**

- 날짜: `M/D (요일)`. 연속일 묶기 가능: `7/15~7/16 (수·목)`.
- 활동: ` / `로 구분. 위키링크 허용. **표 안에서는 파이프를 `\|`로 이스케이프** (`[[노트\|표시명]]`).
- 상태: `✅ 완료` · `🔄 진행` · `-`(휴무) 세 값만.
- 휴무 행 예: `| 7/17 (금) | 제헌절 (휴무) | - | - |`

### `## OKR별 완료 항목`

```markdown
### 상위과제 N: <okr-master의 과제 제목>

#### #okr/<축>/<세부>          ← 복수 태그 묶음이면 `#### #okr/a · #okr/b`

- **[[산출물 노트|업무 제목]] 또는 업무 제목** (M/D~M/D, 완료|진행, 유형) · 부가 표기(요청자·저장소 등)
  - 세부 사실 불릿: 정량 수치·트러블슈팅·의사결정 포함. 여기가 상세의 저장소다.
```

활동이 있는 상위과제·태그만 쓴다. 불릿 머리 이모지는 선택 사항.

### `## 주간 성과 요약`

`| 구분 | 내용 |` 표, 행은 완료 / 진행중 / 정량 지표. 정량 지표는 okr-master의 정량 지표 항목에 대응되게 센다.

### 구조

```
- **카테고리**                                        ← 불릿 + 굵게 (헤딩 아님)
  - [상태] 업무 제목 (M/D~M/D, 상태)                   ← 업무 1건 = 1줄, 2칸 들여쓰기
    - 하위 상세 (M/D, 상태)                            ← 필요할 때만 0~3개, 4칸 들여쓰기
```

- 카테고리 어휘: `AX` · `AI` · `한컴피디아` · `한컴어시스턴트` · `한컴데이터로더` · `Add-Ons` · `SDK` · `기타`. **내용이 있는 카테고리만 쓴다.** `(해당 없음)`으로 채우지 않는다. AX가 맨 앞, 기타가 맨 뒤.
  - **AX**: 소속 팀(AX기술팀) 수행 업무 전반. Agentic OS, 사내 연동·자동화 구축, AI 기술 검토·비교·검증 포함.
  - **기타**: 세미나·시연 참석, 전사 행사, 타 프로젝트 기획서 검토, 개인 연차.
  - 제품 카테고리(피디아 등)는 실제로 그 제품 업무를 했을 때만.
- 업무 제목: **명사형 보고체**("~검토", "~구축", "~평가", "~작성"). 목적·대상이 드러나게. 제목 안에서 부연이 필요하면 콜론을 쓴다(예: "로컬 오픈소스 TTS 검토: Qwen3-TTS의 한국어 업무 문장 품질 평가").
- **프로젝트 애칭·내부 코드네임은 쓰지 않는다.** 로그나 팀 내부에서 부르는 별칭이 있어도 Part 2에는 정식 업무명으로 적는다(Part 1은 애칭 허용). 제목만 읽고 무슨 일인지 알 수 있어야 한다.
- **같은 프로젝트는 단계가 넘어가도 항목을 쪼개지 않는다.** 1차 개발을 마치고 다음 단계(확장·후속 구현)로 넘어갔더라도 Part 2에서는 업무 1건으로 두고 단계별 진행을 하위 상세로 적는다. 상태·기간은 프로젝트 전체 기준(이어지면 `(착수일~, 진행)`). Part 1이 한 항목으로 묶고 있는 업무가 Part 2에서 둘로 갈라져 있으면 정규화 실패다.
- **회의·미팅은 목적을 반드시 밝힌다.** "OO 회의 참석"처럼 회의 이름만 적지 않는다. 제목에 **무엇을 논의·결정하기 위한 회의**인지 담고(예: "체험판 구현 범위·우선순위 확정 회의"), 하위 상세에 **결과**를 적는다: 확정된 방향, 도출된 액션, 남은 재협의 대상. 판단 기준은 **상위 직책자가 인지해야 하는 내용인가**다. (기타의 단순 참석·시연 관람은 예외: "이노스트림 Workflow 시연 참석" 수준으로 충분)
- 모든 업무 항목에 `(날짜, 상태)`: `(7/28, 진행)` · `(7/22~7/28, 진행)` · `(7/24~, 진행)` · `(7/2~7/16, 예정)`.
- 휴무는 **개인 연차만, 날짜만** 쓴다: `개인 연차 (7/27, 7/31)`. 다음 주 예정 연차도 노트에 근거가 있으면 포함. **공휴일·주말은 Part 2에 쓰지 않는다.**
- 상태 접두어 `[완료]`/`[진행]`/`[예정]`은 업무 카테고리 항목에 붙인다. 기타의 단순 참석·연차에는 생략.
- **링크는 외부 URL만** (Confluence·Jira·Figma 등). 노트에서 URL이 확인되는 업무에만 `[__[상태] 제목 (날짜, 상태)__](URL "URL")` 형식으로 제목 전체를 감싼다. URL을 모르면 일반 텍스트로 두고 지어내지 않는다. 업무 하나에 URL이 여러 개면(예: Jira 이슈 3건) 대표 산출물 URL 1개만 쓰거나 일반 텍스트로 둔다.
- 예정 업무도 포함한다.

### 내용 선별: Part 2에서 뺄 것

구현·과정 디테일은 Part 1의 몫이다. Part 2에는 **업무 단위와 결과**만 남긴다.

| Part 1에는 있고 Part 2에는 없어야 하는 것 | Part 2에 남기는 형태 |
|---|---|
| 테스트 건수, CER 수치, 함수·브랜치·파일명, 에러코드, 스캔 횟수 | (제거. 필요하면 "정량 검증 완료" 수준) |
| 트러블슈팅 경과, 인프라 구성 나열 | "셋팅 및 기능 구축 (진행)" 한 줄 |
| 판정·의사결정의 근거 서술 | 판정 결과만 ("대체 불가 판정") |
| `[[위키링크]]`, 이모지, `%% %%` 주석, em dash | (제거. 링크는 외부 URL만, 위키링크는 관련 노트로) |
| 프로젝트 애칭·코드네임 | 정식 업무명 |
| 회의의 논의 경과 전체 | 목적(제목) + 결과 1~2줄(하위 상세) |

## 7. `## 관련 노트`

순서대로:

1. `[[okr-master]]`
2. 직전 위클리: `[[파일명|직전 주간 (M/D~M/D)]]`
3. 본문(Part 1·2)에서 다룬 노트 전부. 경로 포함 링크 권장: `[[10. Project/…/노트|표시명]]`
4. **마지막 줄 = 기간 내 데일리 전부**: `[[YYYY-MM-DD]] · [[YYYY-MM-DD]] · …`
